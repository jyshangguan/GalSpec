Does the JAX IronTemplate_tied agree with the CPU one?

Same template, same kernel parameters, same wavelength grid. Both backends now resample the template onto a grid even in ln(wavelength) at load time (galspec.iron_template.load_iron_template), so a velocity width is one number everywhere. Generated by develop/dev_jax/iron_cpu_vs_jax.py; numbers in io_test/cpu_vs_jax_results.json.

The JAX model now reproduces an independent velocity-space convolution to 0.14% of the iron peak (0.04% at the parameters the IRAS 07546 fit measured) over the range where the template has signal. The CPU class does not: it is 14.6% (14.0%) away from the same reference, and the two models therefore differ from each other by 14.6% (14.0% at the fit parameters). Before this revision the same comparison put the JAX model 4.5% off; what is left now sits in the outermost 100 Å at each end, where the template is truncated and the two implementations pad differently — over the rest of the range it is 0.14%.

2. Distance from the exact answer

The reference shares no code with either model: the template is resampled on a uniform velocity grid and each component is applied there as a Gaussian of sqrt(sigma² − sigma_intr²), so the requested width is the width at every wavelength. gap = max|model − exact| / peak over 4200–5600 Å; 4200–5400 is the same restricted to the range where the template still has signal (everything above 5400 Å is the truncated red end); shape removes the best scale factor; scale is that factor, so +1 % means the model is 1 % brighter than exact.

mock truth (the earlier input/output test): sigma_c = 1980 km/s, amp_w0 = 0.78, dv_w0 = -520 km/s, sigma_w0 = 6400 km/s.

3. What is left on the CPU side

Changing one internal setting of the CPU algorithm at a time moves its profile by up to 49.6% of its own peak (intrinsic width 200 → 340 km/s), 6.2% (kernel window ±10 000 → ±40 000 km/s) and 12.4% (Wiener filter off), at the mock parameters. None of the three brings it closer to the exact profile, so these are not refinements of a converging approximation: they are internal choices, and the "as written" answer is where their errors happen to cancel best. The worst of them leaves it 32.6% from the exact answer.

4. The JAX residual is the truncated ends

At 4200–5400 Å the JAX model is 0.14% from an implementation that shares no code with it, across every kernel width tested (0.01% at the narrowest, 0.57% at the widest). What is left at the very ends is a boundary convention, not a velocity error: the template is tabulated over 4000–5600 Å, the model mirrors the flux at the edge (as SciPy's gaussian_filter1d does, and as the CPU IronTemplate_new does), and the reference extends it with zero. Evaluating the same smoothings with zero padding instead agrees with the reference to 0.02–0.09%, so that is the whole of the difference; it matters only for the iron wing at 5450–5600 Å.

What this means in practice. The two models are no longer interchangeable even approximately: the CPU class is 15x further from the exact answer than the JAX one, its error is spread over the whole template rather than the ends, and it moves when its internal constants are changed. For fitting, a 14.6% error on the iron peak is four times the 5% flux error the worked example allows and is not absorbed by the iron amplitude alone (the shape column: 14.2%), so it is 3× the 5% flux error the worked example allows. The earlier input/output test saw a 2.6% bias on the iron amplitude and χ²/dof = 0.11 where 0 was expected; that was this model, not the JAX one.
