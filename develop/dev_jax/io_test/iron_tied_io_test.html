1. What the model is now

Each Balmer (and He I) line is described by two models, as in example/wrk_sagan_iras07546.ipynb: a narrow Line_Gaussian tied to the kinematics of [O III], and a broad Line_MultiGauss whose component 0 ("core") and further components ("winds") are all broad Gaussians.

n_ha = jxm.Line_Gaussian(amplitude=..., wavec=6563, name="n_halpha")    # narrow
n_ha.dv.tied    = tie_MultiGauss_dv_c("OIII")          # one shift for all narrow lines
n_ha.sigma.tied = tie_MultiGauss_sigma_c("OIII")       # one width for all narrow lines

b_ha = jxm.Line_MultiGauss(n_components=2, amp_c=..., dv_c=..., sigma_c=...,
                           amp_w0=..., dv_w0=..., sigma_w0=..., name="b_halpha")
line_ha = b_ha + n_ha

The iron has no weights of its own

A Line_MultiGauss already is a weighted sum of Gaussians: its weights are its own component amplitudes, amp_c for component 0 and amp_c * amp_w0 for the wind. The iron needs only the shape of that sum — the template is convolved and renormalised — so the core amplitude is nothing but the unit in which the wind amplitude is expressed, and it cancels exactly. That is why IronTemplate_tied takes the line's kernel parameters and nothing else, and why tying it leaves one free number:

fe = jxm.IronTemplate_tied(n_components=2, amplitude=..., name="FeII")   # core + 1 wind
fe.dv_c.tied     = tie_MultiGauss_dv_c("b_halpha")       # core
fe.sigma_c.tied  = tie_MultiGauss_sigma_c("b_halpha")
fe.amp_w0.tied   = tie_MultiGauss_amp_w0("b_halpha")     # wind, the line's own ratio
fe.dv_w0.tied    = tie_MultiGauss_dv_w0("b_halpha")
fe.sigma_w0.tied = tie_MultiGauss_sigma_w0("b_halpha")

# -> free parameters of the iron: amplitude (and z, which is fixed)

n_components counts total kernel components, so 2 is core + one wind and mirrors Line_MultiGauss(n_components=2). A wind's shift is relative to the core (dv_c + dv_w0), as in the line, so the iron inherits the line's centroid. The kernel is normalised to unit sum, so amplitude keeps meaning "the iron scale" whatever the line does.

4. Fits

One recipe for every mock: jxm.Line_MultiGauss(2) + jxm.IronTemplate_tied(2) with all five kernel parameters tied, sampled by JNesty (nlive=400, dlogz=0.02). Peak heights are log-uniform from 1e-3 to 3x the brightest pixel, shifts ±2000 and ±8000 km/s — nothing is seeded near the answer. The generators differ only in how the iron was built:

cpu       galspec.IronTemplate_tied + galspec.Line_MultiGauss     (what was asked for)
pixel     independent re-implementation of the JAX convention      (same maths, other code)
velocity  exact convolution in velocity space                      (same physics, other convention)
jax       jxm.IronTemplate_tied + jxm.Line_MultiGauss               (self-consistency)
cpu+noise the cpu mock plus 1% Gaussian noise                      (the realistic case)

4.2 The two components are exchangeable

With the production (wide) priors the posterior is bimodal: this was the one surprise of the test. Component 0 and component 1 play exactly symmetric roles in the profile, so

amp_c' = amp_c * amp_w0     sigma_c' = sigma_w0     dv_c' = dv_c + dv_w0
amp_w0' = 1 / amp_w0        sigma_w0' = sigma_c     dv_w0' = -dv_w0

is the same spectrum to 3.1e-16 of peak (unit check 9), and the iron follows it because it is tied to that same profile. The data therefore cannot say which of the two components is "the core"; only the prior can. The mirror image of the branch a run fills is not an approximation — applying the map above to the equal-weight samples gives the other mode exactly, and both have the same posterior mass:

Left: the two labellings of the same input (solid and dashed) with their components. Right: the equal-weight posterior in the (σc, σw0) plane, and its exact mirror image — two modes of equal mass, each with χ² = 0.

This matters for the science, not just for this test. A single broad line with a core and a wind has two labels for the same two numbers, so a fit reports whichever mode the sampler happened to fill, and a run that fills both halves reports a marginal median that lands between them — a width that matches neither. The ordering prior used in 4.1 is the cure, and it is also what the words mean: the core is the narrower of the two broad components. With sigma_c ∈ 300–3000 and sigma_w0 ∈ 3000–25000 km/s every parameter comes back, as the table in 4.1 shows.

5. The two ion-shape differences, explained

Same six parameters, four constructions of the same iron. Lower panel: each curve minus the JAX model, in percent of the peak.

5.1 The CPU IronTemplate_tied is a different function (10.3%)

  • It deconvolves the template by a Gaussian of ls_km/1500 ≈ 200 km/s with an FFT division, then smooths the result with scipy.signal.wiener, then convolves with the kernel.
  • The JAX model never deconvolves: for a Gaussian component, smoothing by sqrt(σ² − σintr²) turns a profile of width σintr into one of width σ exactly. Check 2 measures that identity: 2498.7 km/s recovered from a 2500 km/s request.
  • The two classes also disagree about the template's own intrinsic width: ls_km/1500 ≈ 200 km/s there, 800/2.3548 ≈ 340 km/s in IronTemplate_new and in the JAX models. And scipy's wiener(arr, 3) is a local smoothing filter, not a Wiener deconvolution, so it removes part of the structure the deconvolution was meant to restore.

Consequence: the CPU mock recovers the line exactly and the iron scale to -2.6%, but its iron shape leaves a 0.33σ rms residual that no tie can absorb. Nothing here is a JAX error — the same fit to a mock built by the JAX construction returns the input.

5.2 Where the model itself is approximate (4.3%)

The template is sampled linearly in wavelength (2 Å over 4000–5600 Å), so one channel is 150 km/s in velocity at the blue end and 107 km/s at the red end. The model smooths with a constant pixel width, so the velocity width it actually applies is -29% smaller at the red end than the one that was asked for. Both the CPU IronTemplate_new and the JAX models do this, which is exactly why their parity is 1e-16: the convention is shared, not ported.

The velocity row quantifies it: an exact velocity-space convolution differs from the JAX iron by 4.3% of peak and pulls the iron amplitude by -2.1%. If the iron width is ever quoted in km/s, resampling the template onto a logarithmic wavelength grid (uniform in velocity) would make the two agree; the models are otherwise identical.

5.3 One bug this test found, now fixed

The static convolution kernel is sized from the widest width the model may be asked for. Outside a fit that was the constructor default (2000 km/s), so evaluating the tied iron at σ = 6400 km/s truncated the kernel at 2.6σ instead of 4σ — a 0.05% error, which is what this test measured before the fix. IronTemplate_tied now sizes the kernel from the widest sigma_c/sigma_w* actually given (a fit still overrides it with the prior bound), and the pixel-space check below is at 1.2e-13%.

6. What this establishes

  • The tied kernel is the line profile. Scaling the line's peak by seven leaves the iron flux unchanged to 4.5e-15 (check 3): the kernel is normalised and carries no weight parameter.
  • Core and wind are both tied. All five kernel parameters resolve onto the broad line (check 4); the posterior keeps exactly one free iron number, the amplitude.
  • The convolution is implemented correctly. An independent convolution written from the same formula agrees to 1.2e-13% of peak (check 6); the quadrature identity holds analytically (check 2); one kernel component reproduces IronTemplate bit for bit (check 1).
  • A fit to its own model reproduces the input. With the ordering prior the jax row returns all seven parameters with a worst pull of 0.02σ and a profile difference of 0.484%; the pixel row, an independent implementation of the same maths, gives 0.05σ and 0.484%.
  • The two broad components are exchangeable (4.2), exactly and by construction: the profile cannot tell "core" from "wind". Any fit that reports those two labelled widths needs an ordering prior, otherwise the numbers are a coin flip between two identical solutions. This affects the science numbers of the production fit, not just this test.
  • The CPU tied model cannot serve as the truth standard. 10.3% of peak apart, for the reasons in 5.1. If the two are ever compared as a parity test, that construction has to be reconciled first.
  • One model-level approximation is now on record (5.2): a constant-pixel kernel on a linear-wavelength template makes the applied velocity width drift by -29% across the template.
