Does the JAX IronTemplate_tied agree with the CPU one?

Same template, same kernel parameters, same wavelength grid. Generated by develop/dev_jax/iron_cpu_vs_jax.py; figures and numbers in io_test/cpu_vs_jax_results.json.

They agree in shape and scale to a few per cent, but not to machine precision, and the CPU one cannot be the reference. At the parameters of the earlier mock the two models differ by 10.2% of the iron peak (11.4% at the parameters the IRAS 07546 fit measured). Measured against an exact velocity-space convolution, the JAX model is the closer of the two: 4.5% vs 8.5% on the mock parameters, 5.7% vs 9.6% on the fit parameters. Both numbers are conventions, not porting errors, but the JAX convention is a single documented one, while the CPU value moves by up to 21.4 points of peak depending on three internal numerical settings that a user cannot see.

2. Distance from the exact answer

The reference shares no code with either model: the template is resampled on a uniform velocity grid and each component is applied there as a Gaussian of sqrt(sigma² − sigma_intr²), so the requested width is the width at every wavelength. gap = max|model − exact| / peak; shape = the same after removing the best scale factor; scale = that factor, so +1 % means the model is 1 % brighter than exact.

3. Which detail causes what

Changing one internal setting of the CPU algorithm at a time moves its profile by up to 16.3% of its own peak (intrinsic width 200 → 340 km/s), 5.3% (kernel window ±10 000 → ±40 000 km/s) and 0.3% (Wiener filter off), at the mock parameters. None of the three brings it closer to the exact profile — the gap in section 2 does not improve in any of those rows — so these are not refinements of a converging approximation: they are internal choices, and the "as written" answer is the one where their errors happen to cancel best. The three together leave it 14.4% from the exact answer.

4. The JAX model's own 4.5%

That residual is one convention, and it is shared with IronTemplate_new — the pair CPU vs JAX of that model agrees to 1e-16, because both smooth with a constant pixel width. The template spans 4000–5600 Å at 2 Å per channel, so one channel is 150 km/s at the blue end and 107 km/s at the red end: the applied velocity width shrinks by 29% across the template. Resampling the template onto a logarithmic wavelength grid at construction, and smoothing there, would remove it and make the JAX model exact in velocity space. It would not bring the two models any closer, because the CPU departures are larger.

What this means in practice. The two models are interchangeable for fitting: a few per cent of the iron peak is inside the 5% flux error the worked example uses, and most of the difference is a scale factor that a fit absorbs into the iron amplitude — for the same shape the CPU iron is 2.3% fainter than the JAX one at the mock parameters (3.3% at the fit parameters). They are not interchangeable in a verification test: a mock generated with the CPU class cannot be recovered to better than a few per cent by the JAX model, which is exactly what the earlier input/output test saw — χ²/dof = 0.11 instead of ~0, and a 2.6% bias on the iron amplitude. That number measured the CPU model, not the JAX one.
