CPU and JAX IronTemplate_tied: the same function

Same template, same kernel parameters, same wavelength grid. Both backends load the template through galspec.iron_template.load_iron_template, which puts it on a grid even in ln(wavelength) (so a velocity width is one number everywhere) and extends the tabulated range with zeros (so nothing is reflected or invented beyond it). Generated by develop/dev_jax/iron_cpu_vs_jax.py; numbers in io_test/cpu_vs_jax_results.json.

The two models now agree to 3.7e-14% of the iron peak — machine precision, so they are the same function, not two approximations to it. Both are 0.008% from an independent velocity-space convolution at the mock parameters and 0.017% at the parameters the IRAS 07546 fit measured, over the whole 4200–5600 Å range including the truncated ends.
What this replaced. The CPU class used to FFT-deconvolve the template by a 200 km/s intrinsic Gaussian, smooth the result with a Wiener filter, and convolve with a kernel sampled on a fixed ±10 000 km/s window. That was 8.5% from the exact answer at the mock parameters (12.9% even with all three constants corrected), and 8.5% in the 4200–5400 Å range where the template has signal. The algorithm is kept in this script as legacy_iron() so the numbers stay reproducible; it is not in the package any more. Section 3 has the details.

2. Distance from the exact answer

The reference shares no code with either model: the template is resampled on a uniform velocity grid and each component is applied there as a Gaussian of sqrt(sigma² − sigma_intr²), so the requested width is the width at every wavelength. gap = max|model − exact| / peak over 4200–5600 Å; 4200–5400 is the same restricted to the range where the template still has signal (everything above 5400 Å is the truncated red end); shape removes the best scale factor; scale is that factor, so +1 % means the model is 1 % brighter than exact.

The residual is not zero because the template is sampled at 126 km/s per channel: a Gaussian of width σ can only be stored as samples of that Gaussian, so the narrowest kernels lose a fraction of a per cent to the grid (0.47% at σw0 = 400 km/s, where six channels describe the whole kernel). The exact reference has the mirror-image limitation: it integrates on a 10 km/s grid. Everything above σw0 ≈ 1500 km/s agrees to a few hundredths of a per cent.

3. What the fix was

same as the JAX modelyes, to 1e-15 (checked by tests/test_model_features.py) no: 8–10% apart, and the difference moved with every constant

Each constant of the removed algorithm was worth a visible fraction of the iron peak: the intrinsic width 92.6% of the profile (200 → 340 km/s), the kernel window 5.3% (±10 000 → ±40 000 km/s). Correcting all three together left it 12.9% from the exact answer — worse than where it started (8.5%) — and deconvolving by the width the template was actually measured at made it 90%. That is the signature of an inverse problem with no right answer: the deconvolution divides by a narrow Gaussian, so what dominates the result is whatever the filter was tuned to rather than the physics.

4. Over a factor of 22 in kernel width

What this means in practice. The CPU and JAX models are interchangeable: a fit gives the same answer on either backend, and the 0.01% that both still carry is the template's own sampling, not an artefact of either implementation. Before this revision they differed by 8–10%, which is why the earlier version of this page had to report the two backends separately.
