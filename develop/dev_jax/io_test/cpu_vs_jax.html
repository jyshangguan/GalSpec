Does the JAX IronTemplate_tied agree with the CPU one?

Same template, same kernel parameters, same wavelength grid. Both backends load the template through galspec.iron_template.load_iron_template, which puts it on a grid even in ln(wavelength) (so a velocity width is one number everywhere) and extends the tabulated range with zeros (so nothing is reflected or invented beyond it). Generated by develop/dev_jax/iron_cpu_vs_jax.py; numbers in io_test/cpu_vs_jax_results.json.

The JAX model reproduces an independent velocity-space convolution to 0.01% of the iron peak (0.02% at the parameters the IRAS 07546 fit measured), and that is the whole template, ends included. The CPU class does not: it is 8.5% (10.0%) away from the same reference, and the two models therefore differ from each other by 8.5% (10.0% at the fit parameters). Section 3 shows where the CPU error comes from and what happens to it when its internal constants are corrected one at a time.

2. Distance from the exact answer

The reference shares no code with either model: the template is resampled on a uniform velocity grid and each component is applied there as a Gaussian of sqrt(sigma² − sigma_intr²), so the requested width is the width at every wavelength. gap = max|model − exact| / peak over 4200–5600 Å; 4200–5400 is the same restricted to the range where the template still has signal (everything above 5400 Å is the truncated red end); shape removes the best scale factor; scale is that factor, so +1 % means the model is 1 % brighter than exact.

3. What is left on the CPU side

Changing one internal setting of the CPU algorithm at a time moves its profile by up to 92.6% of its own peak (intrinsic width 200 → 340 km/s — the width the template was actually measured at, so this is the correction), 5.3% (kernel window ±10 000 → ±40 000 km/s) and 6.2% (Wiener filter off), at the mock parameters. The kernel window moves it away from the exact profile (8.5% → 11.7%); turning the Wiener filter off moves it very slightly closer (8.5% → 8.0%); and correcting the intrinsic width to the 340 km/s the template was actually measured at takes it from 8% to 90%, because the deconvolution then divides by a much narrower Gaussian and amplifies whatever it finds there. The "as written" answer is where these errors happen to cancel best, not where the algorithm converges, and the worst variant leaves it 89.8% from the exact answer.

4. Where the JAX residual went

The JAX model is 0.01% from an implementation that shares no code with it, across every kernel width tested (0.01–0.47%, narrowest kernel first). Two changes got it there. The template is resampled onto a grid even in ln(wavelength), so a velocity width is one number everywhere instead of one number at the blue end. And the tabulated range is extended with zeros by 100 000 km/s on each side when it is loaded, so the smoothing has no edge flux to reflect and none to invent. Before the second change the model carried the template's last-channel flux out over the truncated red end and kept it there: that was 3.8% of the 4% full-range error, and it was the reason the 4200–5400 Å column had to be reported separately at all. There is nothing to exclude now.

What this means in practice. The two models are not interchangeable even approximately: the CPU class is 1124x further from the exact answer than the JAX one, its error is spread over the whole template, and it moves when its internal constants are changed — the correction that ought to help takes it from 8% to 90%. For fitting, a 8.5% error on the iron peak is 1.7× the 5% flux error the worked example allows, and it is not absorbed by the iron amplitude alone (the shape column: 8.4%), which is what a line and a pseudo-continuum fitted together would need in order not to care.
